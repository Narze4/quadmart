QuadMart keyboard and settings regression checks
October 31, 2026 (America/New_York)

Implemented:
- Shared native modal keeps background controls inert. Sale starts at Cancel;
  filters start at Close. Escape/backdrop dismissal restores the trigger and
  body scroll. A pending sale remains open, preventing accidental dismissal.
- Sale failures use an announced alert, preserve the buyer and permit retry.
- Mobile filters close when resizing to desktop without clearing filter values.
- Filter/search/category state and settings inputs have accessible names or
  state. Settings feedback uses status/alert semantics.
- Settings uses the shared twelve-character password minimum instead of the old
  six-character guidance. Policy, network, throttling, App Check and recent-login
  failures have fixed safe guidance without raw SDK diagnostics.

Local validation:
- Lint passed; five auth-guard tests passed, including safe password-change errors.
- Next.js production-mode emulator build passed with --webpack. Local Turbopack
  was blocked by its worker-port sandbox restriction; CI still uses Turbopack.
- tests/keyboard-browser.mjs passed 12 scenarios in Chromium and WebKit, using
  separate synthetic seller/buyer contexts and only demo-quadmart emulators.
- Checks covered safe initial focus, forward/reverse Tab, Escape and trigger
  restoration; busy-sale dismissal/duplicate rejection; simulated sale failure
  followed by a real emulator sale and the buyer's purchase receipt; filters at
  390px and resize to 1280px; named settings fields, profile update and cancelled
  closure; short-password blocking, simulated server policy rejection, retained
  input/retry and successful local password change. Old login was rejected and
  new login accepted. The buyer account remained available.
- Zero unexpected page errors in the passing run; no error whitelist added.
  Tests use app links instead of artificial full-document reloads between pages
  to avoid WebKit's known loopback long-poll cancellation on unload.
- Screenshots of mobile filters and the sale retry were visually reviewed.
- Added to the full integration runner, so CI repeats this coverage.

Scope:
No real emails, hosted password changes, cloud account changes, production
changes or student invitations. This is not a physical-phone, screen-reader,
full WCAG, hosted password-reset, fresh-signup or launch-readiness result.
The draft PR records CI and the development deployment for the published commit.

November 1 verification follow-up:
CI run 74 failed twice in the existing WebKit verification-failure assertion.
The Firestore security-rule tests passed in both attempts. Safe local diagnostics
then reproduced the failure: the verification flow reached /login instead of
retaining its retry, after two simulated failed token exchanges.

The account moderation listener was sharing setupError with the token/profile
provisioning flow, and a normal safety snapshot could clear that unrelated error.
The Auth provider now keeps account-scoped safety errors separate, ignores stale
listener callbacks and restarts safety listeners on an explicit account retry.
The regression waits for verification-view initialization, installs the transport
failure before changing Auth state and proves a failed response was delivered.
It retains the required visible error and usable retry assertions; no timeout was
increased and no failure was ignored. Failure output includes only synthetic-test
stage, safe UI state and exchange counts, never tokens or email action codes.

The development PR records exact final CI results for this follow-up. The two
failed attempts remain historical evidence, not passing validation. No production
rules, data, credentials, billing, recovery runtime or real password were changed.
