WHAT THE GATE DOES
When enabled, a verified Emory mailbox and an active, server-owned approval for
that exact Firebase Auth UID are both required for marketplace access. Profile
provisioning, ordinary API operations, protected photos and direct Firestore
reads/deletes are covered. Contact/new trades also check the other participant's
membership inside the operation transaction. A reviewer still has the existing
scoped moderation-evidence photo access; it requires an admitted moderator.

The browser observes the policy and its own membership. Revocation removes the
private app view in an open session; API/rules checks do not rely on that UI or
on an old token being refreshed. Retry after approval reruns account setup.
Read failures/malformed enabled policy do not grant admission. Email verification,
suspension, closure, campus boundaries and existing request budgets still apply.
Recently authenticated account-closure operations remain available at the API
boundary even if beta membership has been revoked.

This restricts marketplace admission, not Firebase Auth account creation. Someone
can still attempt signup/verification and receive the invitation-only screen;
Auth App Check/abuse controls remain necessary. The gate does not prove current
enrollment, send invitations, grant moderator roles or change Vercel protection.

SERVER-OWNED DOCUMENT CONTRACT
betaSettings/access:
  { "mode": "invite-only", "campusId": "emory.edu" }
betaAccess/<verified-testers-auth-uid>:
  { "active": true, "campusId": "emory.edu" }

Only the owner/operator may write these through approved administration. The web
client has get access to the policy and its own status, and no list/write access.
Do not put emails, private notes, invitation codes or credentials in these docs.
Set active=false to revoke; do not delete the global policy to suspend a beta.
Keep reviewer/moderator role decisions separate from ordinary beta admission.

IMPORTANT DEFAULT
An absent betaSettings/access preserves protected development behavior only.
The beta client/server and generated firestore.beta.rules now deny missing
policy; firebase.beta.json selects those generated rules. These changes are
locally tested but not deployed. Absence is NOT an acceptable beta configuration. Before exposing the
beta hostname, confirm the policy exists, has the exact contract and denies an
uninvited verified user at both HTTP and direct Firestore boundaries. A present
but unknown/incomplete policy denies access. Configuration read failures deny
requests; they are never treated as an absent document.
