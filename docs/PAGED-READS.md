# Marketplace and account-page loading

The marketplace previously read only the newest 100 active campus listings and applied all filters to that truncated set. Chat detail also stopped at the newest 100 messages; the inbox listened to every conversation.

The marketplace now loads up to 24 matching listings per action, using document-snapshot cursors and an explicit document-ID tie breaker. Category and condition are database filters; newest/price ordering happens in Firestore across the entire matching collection. Title substring and price-range matching preserve the existing behavior. Because Firestore does not provide substring search, a request scans at most four 25-document batches. An empty batch can still have a continuation cursor. The screen says that only the current batch is empty and offers Continue searching; it reports a complete search only after the cursor reaches the end. A dedicated search service remains a future improvement for larger campuses.

Filter changes are debounced by 300 ms and replace the feed. In-flight responses from the old filter, identity or retry cannot populate the new results. Failed additional pages retain existing results and their cursor; retry does not duplicate items. An invalid price range is shown before results. Listing totals describe loaded results, not an invented total for the campus.

The inbox and conversation view keep a live head of 30 items (31 queried for lookahead), then fetch older pages on demand. Timestamp ties use document IDs, and duplicate items are merged by ID. When new activity moves the live boundary, the visible cache stays within the number of requested pages. A burst/disconnect with no overlap resets the window and discards in-flight old-history pages so a hidden gap cannot be skipped. Loaded history can be fetched again from the new cursor. A complete live result removes obsolete cached entries.

Conversation history preserves the scroll offset when older messages are inserted. New messages follow the bottom only when the reader was already near it or just sent a message. Conversation changes remount the view so names, draft/send state and message history do not carry between threads. Access failures clear retained private messages and show recovery instructions. No campus, verification, participant, block or suspension rule was weakened.

`npm run test:pagination` runs the controller and query tests. `npm run test:integration` now includes the browser regression after the buying/selling HTTP checks, using the same production build and isolated emulators; install Chromium with `npx playwright install chromium` for local use. CI installs Chromium and its Linux dependencies. Optional screenshots go only to `QUADMART_SCREENSHOT_DIRECTORY`.

Validation uses pure controller tests for retries/races/live rollover, Firestore emulator tests with more than 100 listings and tied timestamps, and a browser regression against synthetic local data. New development composite indexes cover category/condition combinations with newest and both price orders, plus participant/last-message inbox order. Confirm index readiness before publishing a deployment that uses these queries.

Notifications now keep a live head of 30 items and fetch older pages on demand. The header listens to at most 100 unread records and displays 99+ when capped. The page labels its unread count as belonging to the loaded list. Mark-read actions acknowledge at most 30 selected loaded items per atomic batch, update older loaded rows after the commit, and expose failed writes for retry. Server-confirmed snapshots exclude cache-only and pending-write events. New notifications still arrive live, and links open after successful acknowledgement. An account change remounts action state and cancels old navigation callbacks.

Purchases fetch 24 receipts plus one lookahead and retrieve display names only for distinct sellers in that page (at most 24 extra document reads). A missing/inaccessible optional seller profile does not hide the receipt. The page uses persisted transaction review flags and transaction-specific review links. It describes completed trades; the former Pending/Expired tabs were fixed zero-value placeholders and have been removed. The app does not process payments or maintain buyer reservation/checkout states. Refresh purchases reloads receipts, review status and optional seller names. Unavailable sellers keep their receipt but show Review unavailable instead of a broken review link.

Public profiles fetch their public header separately from 24-item listing and review pages. Each collection has independent loading, retry and cursor state. Tab switches retain loaded pages; profile or viewer changes replace them. Missing or inaccessible headers show Profile unavailable with retry and a marketplace link, rather than a permanent spinner. Listing/review failures retain the header and any successfully loaded other section. Scores and transaction totals still come from the server-owned public profile; visible item counts describe only loaded pages.

Additional-page failures retain rows and cursor for retry. Access denial invalidates any in-flight history response before clearing private rows, so a late success cannot refill a denied view. New query shapes reuse existing development indexes; verify native cloud queries because the emulator does not enforce composite indexes.

The dashboard fetches eight recent campus listings plus one lookahead. Search and category selection switch to the same bounded marketplace feed, so older matches remain reachable after the first 100 scanned records. The previous sample-derived popular-category counts were removed; category navigation does not invent campus totals.

My Listings queries seller, campus and status in Firestore, fetching 24 listings plus one lookahead. Active, Reserved and Sold each have a fresh cursor. Status writes preserve version checks and idempotent retry IDs, remove a changed row from the current tab after confirmation, and refresh on stale-version conflicts. One pending status operation disables competing row actions. Counts describe the loaded status rows.

Saved membership remains capped at 200 IDs in the owner-only private profile. It is loaded from server-confirmed snapshots with a timeout, explicit failure/retry and identity scoping. Saves/removals use atomic array operations and expose rejected writes without silently changing a heart. Each page resolves at most 24 saved IDs, newest save first, followed by one server read to verify current account access. Individual missing or inaccessible listings become removable, generic unavailable slots without revealing their contents. Network failures retain the previous page and cursor. An account-access denial clears the page. Direct document reads preserve the existing rules for missing/foreign entries; no access rule was relaxed. A membership change deliberately resets the saved feed to avoid skipping or reintroducing items after offsets shift. Sold/reserved cards can still be removed.

The sale buyer picker now pages 24 listing conversations plus one lookahead, and fetches at most 24 candidate public profiles per page. Missing/inaccessible candidates are skipped, other errors are retryable, and the user must explicitly choose a buyer or an off-platform sale. A failed or still-loading candidate list cannot silently become an off-platform sale. The new seller/status query needs a listings composite index on campusId, sellerUid, status and createdAt descending; deployment now has 21 development indexes. Native cloud query probes verify index readiness because emulators do not enforce indexes.

The collection browser regression uses two isolated accounts, 223 same-campus listings, 65 initial saved slots and 65 candidate conversations. It covers all three seller statuses, pagination, old search matches, offline retries, denied saved writes/reads, unavailable saves, same-browser account switching, the 200-save cap and a seller-to-buyer sale/purchase/review. The query suite serializes files that reset the same emulator. These are per-query/action bounds, not a server-enforced global read quota. Historical pages are point-in-time reads: changes outside a live head require a fresh visit/reload. Existing write quotas and the full buying/selling checks remain in place.

Reference: [Firestore document-snapshot cursors](https://firebase.google.com/docs/firestore/query-data/query-cursors), [ordering and limits](https://firebase.google.com/docs/firestore/query-data/order-limit-data).
